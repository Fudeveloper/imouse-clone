# HID 与 XP 专用硬件对标测试表

更新时间：2026-06-08

目标：把“iOS 完美控制”拆成硬件层可验证项目。当前仓库实现了 CH9329 串口 HID 原型，但没有接入真实 HID、iMouse XP 专用硬件或 4.4 固件证据。本文件用于采购到硬件后逐步比较，避免把协议猜测当成研发结论。

## 结论先行

- CH9329/通用 HID 只能证明“iPhone 可通过外接指针/键盘被黑盒控制”这个方向，不能证明达到 XP 版的自动绑定、快准狠鼠标模式或多设备稳定性。
- XP 专用硬件到手后，第一件事不是改 GUI，而是做同场对比：枚举方式、绑定方式、点击误差、滑动释放、输入能力、断线恢复、日志证据。
- 如果 XP 专用硬件不暴露标准串口，或者协议不兼容 CH9329，研发任务应转为独立硬件适配，不要继续在 `imouse.hardware.CH9329Device` 里硬塞兼容逻辑。
- 所有硬件测试必须绑定台账：iPhone、iOS、HID 编号、固件、Hub 口、线材、串口、投屏 provider、校准 profile、evidence run id。

## 安全和合规边界

本项目只针对自有或已授权 iPhone 做自动化测试、设备运维和合规业务流程。对 XP 专用硬件的研究以黑盒对标和合法采购测试为主：

- 不绕过授权、加密、许可证或厂商访问控制。
- 不发布或使用来源不明的固件。
- 不把抓包、反编译或协议猜测写成已确认事实。
- 不在未授权账号、第三方平台规避规则、垃圾操作等场景使用。

## 硬件路线对比

| 路线 | 适用阶段 | 优点 | 风险 | 当前研发动作 |
|---|---|---|---|---|
| CH9329/通用 USB HID | P1/P2 原型 | 成本低、串口协议可控、适合 Python 快速验证 | 坐标、滑动、中文输入、断线恢复都要自研 | 保留为最小闭环基线 |
| XP 专用硬件/4.4 固件 | P1 对标/P2+ 主线候选 | 最接近 iMouse XP 真实体验，可能支持自动绑定和优化鼠标模式 | 协议、授权、固件、售后不可控 | 尽早采购一套做黑盒对比 |
| 蓝牙 HID | 概念验证 | 接线少 | 配对、断连、批量管理和唯一绑定困难 | 不作为主线 |
| 自研 HID 固件 | P2/P3 | 可控、可做自动绑定和批量稳定性 | 硬件研发周期长，需要固件/驱动能力 | XP 专用硬件不可控时再评估 |

## P0 离线可验证项目

当前仓库只能离线验证这些：

| 项目 | 命令 | 通过说明 | 不能证明 |
|---|---|---|---|
| CH9329 帧构造 | 单元测试 / `_build_frame` | 帧格式函数能运行 | 真硬件接受、iPhone 响应 |
| 串口枚举函数 | `imouse.hardware.list_devices()` | pyserial 能枚举系统串口 | 新增 HID 存在 |
| 设备绑定 API | `/api/device/bind` | 服务端能记录绑定请求 | 串口真实可打开 |
| 点击/滑动 API | 单元测试 | 请求路由和坐标映射可运行 | iPhone 真点击/滑动 |
| evidence | `imouse.validation` | 能记录观察和失败分类 | 硬件链路成功 |

P0 通过只说明代码底座可测试。它不是硬件通过证据。

执行：

1. 每点点击 10 次。
2. 每次人工观察是否命中目标。
3. 失败时保存截图或录屏路径。
4. 记录平均误差、最大误差和是否有方向性偏移。

通过标准：

- 核心业务按钮误差小于 8 px。
- 连续 50 次点击无漂移。
- 没有按下不释放。
- 误差能通过 calibration profile 解释。

### 5. 断线与恢复

| 故障注入 | 期望 | 结果 | 失败分类 |
|---|---|---|---|
| 拔 HID 后重插 | 能重新绑定，不影响台账 |  | `hid_discovery` / `hid_bind` |
| 拔 iPhone 转接线 | 单设备失败，不影响其他设备 |  | `hid` / `binding` |
| Hub 单口重插 | 其他口不掉线 |  | `hub_power` |
| iPhone 锁屏再解锁 | 指针/键盘恢复 |  | `business_state` |
| 投屏断开但 HID 仍在 | API 能提示链路不完整 |  | `airplay_stream` / `binding` |

P3/P4 以后必须在 4 台、10 台环境里重复这些注入，否则“单台通过”不能外推到群控。

## XP 专用硬件专项

拿到 XP 专用硬件后的第一轮目标不是“接入成功”，而是回答这些问题：

| 问题 | 为什么重要 | 证据 |
|---|---|---|
| 是否暴露标准串口/USB HID/自定义设备 | 决定能否复用当前 `hardware.py` | 设备管理器、VID/PID、doctor |
| 是否需要官方 Core 服务 | 决定是否只能走官方链路 | 安装记录、进程列表 |
| 是否能脱离官方 Console 操作 | 决定第三方 Python GUI 可集成性 | API/curl/日志 |
| 是否支持自动绑定 | XP 体验核心 | 插线到绑定完成的完整录像和日志 |
| 4.4 固件具体带来什么 | 避免只复述宣传 | CH9329 同场对比表 |
| iOS 17+ 鼠标模式是否不同 | 影响坐标、滑动、速度 | 同机同页点击/滑动矩阵 |
| 断线恢复是否自动 | 群控稳定性核心 | 故障注入日志 |
| API 返回是否有设备级错误 | 失败隔离核心 | 调用日志 |

如果只能通过官方 Console 使用，且没有可调用 API 或稳定窗口/日志接口，就把它归类为“竞品体验对照硬件”，不能直接作为我们 Python GUI 的硬件后端。

## 研发适配建议

当前 `imouse.hardware` 是 CH9329 风格实现。后续不要把所有硬件都塞进这个类，应拆成 provider：

```text
HidProvider
  open()
  close()
  health()
  click(x, y)
  swipe(x1, y1, x2, y2, duration_ms)
  type_text(text)
  key(code)
  release_all()
  device_meta()
```

Provider 建议：

| Provider | 状态 | 说明 |
|---|---|---|
| `ch9329` | 当前原型 | 串口帧控制 |
| `xp_hardware` | 待采购 | 是否可实现取决于合法 API/协议 |
| `mock` | 测试 | 单元测试和 dry-run |

设备台账应保存：

```json
{
  "device_id": "dev_1",
  "hid_provider": "ch9329",
  "hid_id": "hid01",
  "firmware": "unknown",
  "serial_port": "COM3",
  "hub_port": "hub-a-01",
  "iphone_id": "ip01",
  "ios": "17.7",
  "capture_provider": "uxplay",
  "calibration_profile": "state/calibration.json:dev_1"
}
```

## Evidence 记录规范

每次硬件动作都至少包含：

- `device_id`
- `hid_provider`
- `hid_id`
- `firmware`
- `serial_port` 或设备路径
- `capture_provider`
- 操作类型：click/swipe/type/key/release
- 请求参数
- API 返回
- 人工观察：iPhone 是否真实响应
- 失败分类
- 截图/录屏/日志路径

## 阶段门

| 阶段 | 硬件要求 | 禁止晋级条件 |
|---|---|---|
| P1 单台 | 至少一套 HID 真实响应 | 没有人工观察、没有截图/录屏、只有 API success |
| P2 单台稳定 | 同一套 HID 连续重复点击、滑动、输入、释放状态检查 | 单台 30 分钟不稳定或失败无法复现 |
| P3 4 台 | 每台独立 HID、线材、Hub 口、投屏名，逐设备失败隔离 | 单台失败会阻塞整组或设备绑定关系不清 |
| P4 10 台 / XP 对标 | 10 台 2 小时稳定性、故障注入，并与 XP 专用硬件或等价自研路线同场对比 | 失败无法归因，或不能解释 4.4/自动绑定/鼠标模式差距 |

## 常见错误判断

- “串口能打开”不等于 iPhone 被控制。
- “鼠标能移动”不等于坐标可交付。
- “CH9329 能点”不等于 XP 专用硬件协议已兼容。
- “官方 Console 能用”不等于 Python GUI 能接入。
- “一次点击成功”不等于 50 次点击无漂移。
- “无线投屏正常”不等于 HID 绑定正确。
- “P1 单台通过”不等于 10 台不会出现 Hub 供电和串口混乱。
