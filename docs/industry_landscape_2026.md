# iOS 群控行业现状与 XP 对标判断

更新时间：2026-06-09

本文优先回答“这个行业现在怎么做、为什么这么做、坑在哪里”。系统实现只是验证这些判断的工具，不是目标本身。

当前公开来源快照和 SOP 决策表见 `docs/industry_current_state_snapshot_2026.md`。本文保留行业路线判断，快照文件用于 2026-06-09 后的来源复核和采购/现场开测会议。

## 结论摘要

- 对标 iMouse XP 时，主路线应是 AirPlay/投屏取画面 + USB HID 输入 + 视觉识别 + 本地 API/控制台。
- WebDriverAgent、Appium、XCUITest 更适合自家 App 测试，不适合“手机端零安装、跨 App、跨系统界面”的 XP 类黑盒群控目标。
- MDM、Apple Configurator、快捷指令适合设备初始化、证书、Wi-Fi、安装包和合规配置，不是像素级控制方案。
- 越狱和私有 API 不建议作为主路线；版本、签名、售后和合规风险会吞掉短期收益。
- 真正的产品壁垒不是能发一个 click，而是投屏稳定、HID 固件、自动绑定、坐标校准、失败隔离、日志证据、分组运营和现场 SOP。

## 公开资料确认

iMouse 官方资料公开呈现的 XP 类产品形态：

- 手机端无需安装 App，使用 AirPlay 镜像传输屏幕。
- 鼠标键盘操作依赖 iMouse 虚拟鼠键硬件。
- 产品由内核服务端和控制台端组成，控制台基于内核 API 实现。
- API 支持 HTTP 和 WebSocket。
- 图像能力包含 OpenCV 找图和 OCR。
- XP API 文档体现出统一 `/api` + `fun` 的调用风格，典型本地服务端口是 `9911`。
- Python XP 开发文档说明 `imouse-py` 是 XP 客户端库，并需要配套 XP 专用硬件。

XP 版迭代资料体现的重点不是“多几个接口”，而是现场体验：

- Windows 10+，建议 8GB 内存起步，有线网络优先。
- 4.4 固件和有线投屏后可自动绑定硬件。
- 投屏连接从十几秒级降到约 1 秒级。
- 单一投屏服务降低资源占用，并支持 H264/H265 硬件解码。
- 多设备窗口分离、刷新效率、多进程显示、横屏、高分辨率、音频解码、Emoji、多语言。
- 分组云端存储、子账号、局域网可见范围、自动更新、调试工具、请求/返回日志。

Apple 侧系统能力提供了路线基础：

- iPhone 可以使用 AirPlay 屏幕镜像。
- iOS 支持鼠标、触控板等指针设备；实际群控产品仍要自己解决硬件、坐标、延迟和稳定性。

## 主流路线对比

| 路线 | 适合场景 | 优点 | 关键短板 | 是否作为本项目主线 |
|---|---|---|---|---|
| XCUITest/WDA/Appium | 自家 App 自动化测试 | 元素级定位、断言清晰、测试生态成熟 | 需要签名、信任、WDA 部署；跨 App/系统 UI 边界明显 | 否，作为辅助测试工具 |
| AirPlay/投屏 + HID | XP 类无越狱群控 | 手机端零安装，跨 App，黑盒可控 | 投屏、HID、坐标、网络、Hub 都是工程难点 | 是 |
| MDM/Configurator | 批量初始化、配置、合规 | 设备管理正规，适合台账和初始配置 | 不是像素级控制，不能点击业务页面 | 辅助 |
| 快捷指令 | 单机轻量流程 | 系统内置、低成本 | 自动化边界窄，难群控，难黑盒 | 辅助 |
| 越狱/私有 API | 特殊实验 | 能力强 | 版本和合规风险高，售后困难 | 不建议 |

## XP 类产品的真实壁垒

1. 投屏服务

投屏不是“能看到一次画面”就结束。XP 类体验需要低延迟、可重连、可多设备、可硬解、可窗口分离、可稳定截图。当前原型的 UxPlay/X11 思路只能做早期验证，不能直接代表 XP 产品级投屏。

投屏 receiver、截图采集、有线投屏和采集卡路线的选型矩阵见 `receiver_capture_selection.md`。

2. HID 硬件与固件

普通 CH9329 可以验证 HID 输入方向，但 XP 的 4.4 固件、自动绑定、iOS 17+ 鼠标模式和多设备稳定性都必须实测。硬件层要记录固件、串口、Hub、线材、iPhone 型号和 iOS 版本，不能只记录“点击 API 成功”。

CH9329、XP 专用硬件和自研 HID 的同场对标表见 `hid_hardware_protocol_benchmark.md`。

3. 坐标和分辨率

iPhone 型号、Retina 缩放、横竖屏、投屏黑边、safe area、灵动岛、Home Indicator 都会改变坐标。必须建立每台设备的校准 profile，并把误差写进 evidence。

4. 视觉资产

找图/OCR 的难点不是调用 OpenCV，而是资产规范：模板必须有纹理，阈值必须可追溯，语言/主题/亮度变化要分层，失败截图要回放。

5. 现场运维

群控现场的问题经常来自 Hub 供电、线材、串口占用、AP 隔离、Bonjour/mDNS、Windows 防火墙、投屏服务版本。SOP 和测试矩阵比 GUI 更早成为核心资产。

6. 失败隔离

XP 类产品必须做到单台失败不拖垮整组。API 返回要按设备给出结果；日志、GUI、脚本和 evidence 都要能追到具体设备 ID。

## 我们的研发顺序

P0：知识和证据底座

- 固化 XP 公开能力、行业路线、SOP、测试矩阵。
- 离线验证 API、GUI、脚本、doctor、evidence。

P1：单设备实机闭环

- 一台 iPhone，固定一套 HID，固定一个投屏路线。
- 完成投屏、截图、五点校准、点击、滑动、输入、找图、OCR。
- 所有通过项都有人工 observation。

P2：单设备稳定

- 同一台 iPhone 连续运行 30 分钟以上。
- 记录截图成功率、HID 释放状态、坐标误差、CPU/内存/网络和失败分类。
- P2 不证明群控，只证明单机链路可以重复。

P3：4 台试点

- 证明分组、批量命令、单台失败隔离。
- 30 分钟稳定运行并记录每台设备的失败分类。
- 不允许用单台 evidence 外推 4 台通过。

P4：10 台稳定与 XP 对标专项

- 2 小时运行，记录 CPU、内存、网络、投屏断线、HID 失败、截图成功率。
- 开始比较不同 Hub、线材、投屏组件。
- 进入窗口分离、日志过滤、自动重连、失败截图自动采集、Windows 原生/有线投屏/硬解专项。
- 20+ 设备只能作为 P4 之后的商业化扩展目标，不能提前写成当前验收阶段。

## 研发禁区

- 不在没有真机 evidence 的情况下宣称“iOS 完美控制”。
- 不把离线单元测试当作硬件通过证据。
- 不在单机坐标不稳定时扩大到群控。
- 不用纯色模板做找图资产。
- 不让一个设备的异常阻塞整组响应。
- 不把 API、GUI、脚本、SOP 分散成互相不一致的三套流程。

## 对当前仓库的判断

当前仓库已经适合做 P0 到 P1 的准备工作：

- XP 风格 `/api` + `fun` 协议层已有初版。
- GUI 能承载设备、硬件、截图、图色、分组、校准、doctor、scenario 和 evidence。
- JSON runner 能把现场流程沉淀为可重复脚本。
- Doctor 能提前暴露 UxPlay、串口、目录、状态文件和服务端口问题。

当前仓库还不能证明：

- 真实 iPhone 投屏稳定。
- HID 硬件对 iPhone 控制稳定。
- XP 专用硬件/4.4 固件兼容。
- Windows 产品级投屏、硬解、有线投屏、多窗口分离。
- 4 台、10 台、20 台的群控现场体验。

下一步不是继续堆 GUI，而是按 `field_test_matrix.md` 用真实硬件补证据。
