# iMouse XP 迭代路径与研发踩坑复盘

更新时间：2026-06-09

目标：把 iMouse XP 公开资料中能观察到的产品迭代线索，转成我们研发可以执行的判断、阶段门和避坑清单。本文不把任何公开宣传直接当成已验证事实；所有 XP 能力都需要在我们的硬件、投屏、网络和 iPhone 组合里重新实测。

## 资料可信度分层

| 层级 | 来源 | 用法 |
|---|---|---|
| 高 | iMouse 官网、XP API 文档、Python XP 文档 | 作为对标能力和 API 形态的主要依据 |
| 中 | BestMoon/some3c 镜像、XP 新版帮助文档、公开行业配置文档 | 用来推断 XP 迭代重点和现场配置，但要复核 |
| 低 | 论坛、博客、卖家口述、二手资料 | 只能作为待验证线索，不能写进验收结论 |

本仓库当前只完成离线验证和 Python GUI 原型。真实 iOS 控制能力仍必须按 `p1_single_device_runbook.md`、`p2_p3_stability_runbook.md` 和 `field_test_matrix.md` 补实机 evidence。

## 公开能力反推的迭代路径

### 阶段 1：先证明免越狱黑盒控制

公开线索：

- iPhone 端无需安装 App。
- 屏幕通过 AirPlay 镜像传输。
- 鼠标键盘操作依赖 iMouse 虚拟鼠键硬件。
- 产品用于 iOS 自动化、批量测试和授权设备批量操作。

它解决的坑：

- Appium/XCUITest 需要签名、信任、WDA 或测试包，跨 App 和系统 UI 边界明显。
- 越狱和私有 API 版本风险大。
- 业务黑盒页面没有元素树，只能看画面、点坐标。

我们的研发动作：

- P1 只追一台 iPhone：能看、能截图、能点、能滑、能输入。
- API 返回成功不算 iPhone 控制成功；必须有人眼观察和 evidence。
- 首批硬件不要贪多，先把投屏组件、HID 模块、Hub 口、线材和 iPhone 编号固定。

验收证据：

- `evidence/<run_id>.jsonl`
- `evidence/<run_id>.md`
- `evidence/<run_id>_doctor.md`
- 截图/录屏/失败附件

### 阶段 2：把能力服务化，控制台只做 API 客户端

公开线索：

- 产品由内核服务端和控制台端构成。
- 控制台基于内核服务端 API 实现。
- API 支持 HTTP 和 WebSocket。
- XP API 围绕本地 `9911/api` 和 `fun` 功能名调用。
- Python XP 文档提供 API/helper 分层。
- PyPI `imouse-py` 包的公开版本节奏可作为 SDK/API 漂移线索，但安装包不能替代 XP 专用硬件、receiver、HID、截图和人工观察。

它解决的坑：

- GUI 和核心能力耦合后，脚本、第三方系统和多语言调用都会受限。
- 群控现场需要批量脚本、日志、回放和外部系统调度，不能只靠人点 GUI。
- WebSocket、`msgid` 和回调能支撑异步事件、状态通知和长任务。

我们的研发动作：

- 保持 FastAPI 内核服务和 GUI 分离。
- 继续扩展 `/api` + `fun`，不要只做 REST endpoint。
- Python GUI 全部通过 `XpApiClient` 调内核服务，不直接绕过 API。
- SDK/包版本需要固定来源、版本和 hash，再用 API 兼容测试验证；不要把 `pip install` 成功当成 XP parity。
- 批量接口必须返回逐设备结果，单台失败不能让整组请求崩溃。

验收证据：

- XP API 单测。
- `curl` 手动验证。
- WebSocket 请求验证。
- 4 台分组时的逐设备返回 evidence。

### 阶段 3：XP 版开始解决投屏性能和窗口体验

公开线索：

- Windows 10+。
- 所有窗口可分离并独立控制。
- 单一投屏服务降低资源占用。
- 支持 H264/H265 硬件解码。
- 全高清显示、高分辨率、横屏、多设备音频解码。
- 投屏连接速度从多秒级优化到接近 1 秒级。

它解决的坑：

- 多设备 AirPlay 接收器如果每台都一套独立进程，CPU、内存和窗口管理会很快失控。
- 无线投屏发现、连接、黑屏、花屏、断线、延迟是 XP 类产品的第一大现场瓶颈。
- 高分辨率 iPhone 和横屏会放大截图、坐标和视频解码问题。

我们的研发动作：

- 当前 UxPlay/X11 路线只作为 P1 原型，不当作 XP 产品级投屏结论。
- P2/P3 必须记录投屏断线、截图成功率、CPU、内存、网络和恢复耗时。
- 尽早比较 UxPlay、Windows Receiver、有线投屏和硬解路线。
- 在内核层抽象 Capture Provider，避免 GUI 绑定某个窗口标题或某个 receiver 实现。

验收证据：

- 100 次截图成功率。
- 黑屏/花屏/断线复盘。
- receiver 版本和日志。
- P4 10 台 2 小时 metrics。

### 阶段 4：4.4 固件、有线投屏和自动绑定降低现场复杂度

公开线索：

- XP 新版资料提到 4.4 固件、有线投屏后自动绑定硬件。
- iOS 17+ 与 4.4 固件相关的鼠标模式需要单独实测。
- Python XP 文档强调必须配套 XP 专用硬件。

它解决的坑：

- 多台设备现场最容易乱的是“画面窗口、HID 串口、Hub 口、iPhone”之间的对应关系。
- 手动绑定出错会导致点 A 画面、动 B 手机。
- 普通 HID 坐标在不同 iPhone、投屏裁剪、safe area 和横竖屏下容易漂移。

我们的研发动作：

- CH9329 只证明通用 HID 路线；不能假设等同 XP 4.4 固件。
- 如果拿到 XP 专用硬件，第一件事不是改 GUI，而是做协议/绑定/误差对比表。
- 自动绑定研发要从 USB 拓扑、串口硬件 ID、投屏名称、设备编号和校准文件关联开始。
- 每台设备必须有物料台账，见 `hardware_test_bench_checklist.md`。

验收证据：

- 插拔前后串口列表。
- XP 专用硬件与 CH9329 对比表。
- 五点校准误差表。
- 单台断开/恢复记录。

### 阶段 5：图色/OCR/脚本能力产品化

公开线索：

- 官网和文档公开提到 OpenCV 找图、百度飞桨 OCR、查找文字、多点找色。
- XP API 有图色、鼠标、键盘、设备、配置、回调等分类。
- Python helper 覆盖 Device、AirPlay、USB、Group、ImConfig、User 等层。

它解决的坑：

- 黑盒业务页面不能稳定依赖坐标，需要视觉定位。
- OCR/找图不是调用库就够，真正难点是模板资产、阈值、区域、主题、语言和失败回放。
- 长流程必须能 dry-run、实跑、记录、复盘，而不是只有一次性脚本。

我们的研发动作：

- GUI 已支持裁剪模板、找图、找色、OCR、找文字，但还缺模板资产库和失败截图自动采集。
- JSON runner 已支持 repeat、metrics、record；下一步需要变量、条件分支和失败截图自动保存。
- 所有图色动作必须记录模板路径、阈值、region、命中坐标和失败截图。

验收证据：

- 模板资产命名规范。
- 有纹理模板通过，纯色模板禁止。
- OCR 首次模型下载和真实图片识别记录。
- 失败可以用截图和模板复现。

### 阶段 6：运维能力成为群控壁垒

公开线索：

- XP 新版资料提到设备列表、分组云端存储、子账号、局域网可见范围、自动更新、调试工具、请求/返回日志、自定义快捷键。

它解决的坑：

- 设备数上来后，现场问题主要是“谁坏了、为什么坏、能否复现、会不会拖垮整组”。
- 多人、多账号、多机器协作需要权限、分组、日志和可见范围。
- 没有请求/返回日志和复盘报告，现场问题无法转成研发任务。

我们的研发动作：

- 当前先做本地分组 JSON，P3 后再考虑云端/账号。
- GUI 新增 Review 复盘，现场可以直接看失败分类、metrics 和建议。
- Evidence JSONL 是现场和研发之间的交接格式，不要用口头描述替代。

验收证据：

- P3 单台失败隔离。
- P4 10 台 2 小时复盘报告。
- Top 3 失败分类进入 backlog。
- 失败设备能在 30 秒内定位。

## XP 踩坑点转研发任务

| 坑点 | 公开线索/工程推断 | 我们的研发任务 | 阶段 |
|---|---|---|---|
| AirPlay 发现不稳定 | 需要同网段、receiver、Bonjour/mDNS | doctor 增加网络/receiver 检查，P1 记录投屏组件 | P0/P1 |
| 投屏黑屏/花屏/断线 | XP 强调单服务、硬解、重连 | Capture Provider 抽象，P2 记录截图成功率和断线 | P1/P2 |
| 窗口和硬件绑定错位 | XP 提到自动绑定 | 设备台账、USB 拓扑、投屏名、串口映射 | P1/P2 |
| 坐标漂移 | 自适应分辨率、横屏、高分辨率 | 五点校准、active/target、safe area、误差阈值 | P1 |
| iOS 版本鼠标行为差异 | iOS 17+ 鼠标模式线索 | iOS 版本矩阵，CH9329 vs XP 4.4 对比 | P1/P2 |
| HID 按下不释放 | HID 固件/协议风险 | click/swipe/type 压测，记录释放失败 | P1 |
| 纯色模板误判 | OpenCV 匹配固有问题 | 模板资产规范，禁止纯色模板 | P1 |
| OCR 首次下载/缓存失败 | PaddleOCR/PaddleX 环境依赖 | 项目内缓存、离线模型策略、真实 OCR evidence | P1 |
| 单台失败拖垮整组 | 群控常见现场问题 | 批量接口逐设备返回，P3 故障隔离必测 | P2/P3 |
| GUI 看不出谁坏 | 多设备运维问题 | 日志过滤、Review 报告、按设备状态列 | P2 |
| 资源瓶颈不可解释 | XP 强调硬解和单服务 | metrics、receiver 日志、2 小时稳定性曲线 | P3/P4 |
| 权限/分组混乱 | 子账号、云端分组线索 | 本地分组先稳定，再设计账号/云同步 | P3 |

## 我们不要照抄的部分

- 不要先做漂亮多窗口 GUI，再回头补投屏和 HID；这会把最硬的问题藏起来。
- 不要把 UxPlay 原型路线当成 XP Windows 产品级投屏。
- 不要在没有 XP 专用硬件实测前实现“4.4 固件兼容”口号。
- 不要让脚本只记录 API 成功；必须有人工 observation。
- 不要把云端分组、账号权限提前做成复杂系统；P3 之前本地分组足够。
- 不要把 OCR/找图能力写成“已完成”，除非有真实截图、模板、阈值和失败回放。

## 研发路线建议

### 当前 P0：可验证原型

已做：

- XP 风格 `/api` + `fun`。
- Python SDK 初版。
- Tkinter GUI 原型。
- doctor、evidence、Review 复盘。
- JSON runner、repeat、metrics。
- P1/P2/P3/P4 runbook。

仍缺：

- 真实投屏组件。
- 真实 HID 硬件。
- XP 专用硬件/固件对比。
- 真实 iPhone evidence。

### 下一步 P1：单台闭环

只做一台：

- 选定投屏路线。
- 插入 HID。
- 五点校准。
- 点击、滑动、输入。
- 截图、找图、找色、OCR。
- 生成 Review 报告。

通过后才进入 P2。

### P2/P3：稳定性和群控

- P2 两轮单台 30 分钟。
- P3 四台 30 分钟，必测单台故障隔离。
- 每轮失败 Top 3 回填 backlog。

### P4/P5：XP 体验专项

- 10 台 2 小时。
- Windows 原生/有线投屏/硬解专项。
- 自动绑定专项。
- 模板资产库和失败截图自动采集。
- 日志过滤、实时网格、多窗口显示。

## 需要向供应商或现场继续确认的问题

采购 XP 专用硬件时优先问：

- 是否暴露标准串口、HID 或私有驱动。
- 固件版本如何查看和升级。
- 4.4 固件与 iOS 17+ 鼠标模式的具体限制。
- 自动绑定依赖有线投屏、硬件序列号、设备名还是服务端配置。
- 单 PC 推荐设备数、Hub 要求和供电要求。
- 投屏组件是否支持有线、H264/H265、硬解和多设备单服务。
- 是否有错误码、日志路径、回调事件文档。
- 授权方式是否绑定硬件、PC、账号或局域网。

这些问题的答案应写入 `hardware_test_bench_checklist.md` 的采购验收报告，而不是只存在聊天记录里。
