# iOS 群控 SOP 与常见问题

更新时间：2026-06-08

适用范围：自有或已授权 iPhone，用于自动化测试、设备运维、批量配置、合规业务流程。不要用于未授权账号、平台规避、垃圾操作或其他违法用途。

## 角色与物料

### 人员

- 研发：负责内核服务、GUI、协议、视觉能力。
- 测试：负责设备矩阵、场景脚本、回归。
- 现场运维：负责线材、Hub、网络、设备标签、故障替换。

### 硬件

- Windows 10 或更高版本电脑，建议 8GB 内存起步，多设备建议 16GB 或 32GB。
- 有线网络优先，避免 PC 走 Wi-Fi。
- iPhone 测试机，至少覆盖 iOS 13.4、iOS 16、iOS 17、iOS 18 及更新系统。
- 每台 iPhone 对应一套 HID 控制硬件。
- 带独立供电的 USB Hub。
- 高质量数据线、OTG/转接线。
- 设备标签：手机编号、硬件编号、线材编号、Hub 口编号。

## 初始化 SOP

1. 建立设备台账

记录字段：

- 设备编号。
- iPhone 型号。
- iOS 版本。
- 屏幕分辨率。
- 硬件编号。
- 固件版本。
- USB 端口。
- 常用投屏名称。
- 备注和故障历史。

2. PC 环境检查

最低检查：

```powershell
py -0p
.\.venv\Scripts\python --version
.\.venv\Scripts\python -m imouse.main --check
.\.venv\Scripts\python -m imouse.doctor --markdown evidence\preflight_YYYYMMDD.md
```

通过标准：

- Python 使用 3.13。
- `serial`、`cv2`、`numpy`、`PIL`、`fastapi`、`uvicorn` 全部 OK。
- 投屏服务如果使用当前仓库的 UxPlay 路线，则 `uxplay` 必须能找到。
- doctor 报告中没有 `fail`；如果使用替代投屏服务，必须记录替代组件名称、版本和路径。
- 插入 HID 硬件后，doctor 的 `serial_ports` 能看到新串口。

3. 网络检查

- PC 和 iPhone 在同一局域网。
- 关闭 AP 隔离、访客网络隔离。
- 放行 Bonjour/mDNS 发现所需流量。
- 防火墙放行服务端口。
- 多设备测试建议 PC 使用有线网络。

4. iPhone 设置

建议：

- iOS 覆盖至少从 13.4 起步；新机型和新系统要单独入矩阵，不能只测一台最新系统。
- 关闭自动锁屏或设为最长。
- 保持电量充足或接电。
- 关闭影响画面稳定的弹窗和自动更新提示。
- 确认鼠标/键盘硬件接入后系统能响应。
- 横竖屏测试前锁定或明确记录方向策略。
- 打开 `设置 > 辅助功能 > 触控 > 辅助触控`，并记录菜单是否常显、跟踪灵敏度。
- 打开 `设置 > 辅助功能 > 键盘 > 全键盘访问`，记录自动隐藏时间。
- 连接硬件后检查 `设置 > 通用 > 触控板与鼠标`，把跟踪速度策略固定下来。
- `显示与亮度` 里固定亮度、自动锁定、显示视图，避免脚本跑一半被亮度变化或锁屏干扰。
- 控制中心布局要固定；投屏入口必须稳定可见，避免自动投屏或人工重连时多一步找入口。

5. 硬件接线

原则：

- 一台 iPhone 对应一套 HID 硬件。
- 每个 Hub 口和设备编号固定绑定。
- 批量场景必须用带独立供电的 Hub。
- 接线完成后先只测一台，不要一开始全接。

6. 投屏连接

单设备标准流程：

- 启动内核服务。
- 启动投屏服务。
- iPhone 选择对应 AirPlay 接收端。
- 服务端显示设备在线、分辨率已识别。
- 截屏接口返回画面。
- 手动取点并点击一个无风险 UI 区域。

投屏组件选型、receiver 元数据记录和截图质量验收见 `receiver_capture_selection.md`。现场临时更换 receiver 时，必须记录组件名称、版本、路径、启动命令和截图采集方式。

7. 坐标校准

每台设备必须校准：

- 在 GUI 中点击 `Screenshot`，确认截图尺寸。
- 在 `Coordinate Calibration` 面板点击 `Use Screenshot`。
- 如有黑边、裁剪、标题栏或投屏边框，调整 `Active x/y/w/h`。
- 如硬件坐标空间与截图尺寸不同，调整 `Target w/h`。
- 勾选 `Enabled` 并点击 `Save`。
- 左上角。
- 右下角。
- 中心点。
- 刘海/灵动岛区域。
- 底部 Home Indicator 区域。
- 横屏模式。

校准通过标准：

- 点击误差小于 8 像素，核心按钮区域不误点。
- 连续 50 次点击无明显漂移。
- 滑动轨迹方向正确，起止点可控。
- 每个点位都要用 `Manual` 记录人工观察，失败时保存截图或录屏路径。
- 校准 JSON 和 evidence run id 必须写入现场记录。

## 单设备验收流程

1. 能投屏

验收：

- 画面清晰。
- 分辨率正确。
- 延迟可接受。
- 断开后能重连。

2. 能截图

验收：

- 截图不是黑屏。
- 截图尺寸与设备记录一致。
- 连续 100 次截图无异常。

3. 能点击

验收：

- 点击 10 个坐标点。
- 每点点击 10 次。
- 不出现坐标反转、缩放偏移、越界。

4. 能滑动

验收：

- 上下左右滑动各 20 次。
- 长短滑动各 20 次。
- 不出现鼠标按下后未释放。

5. 能输入

验收：

- 英文、数字、符号。
- 中文输入需要单独确认输入法策略。
- Emoji 需要单独确认，不作为第一阶段刚需。

6. 能找图

验收：

- 使用有纹理模板，不用纯色模板。
- 相同按钮在不同亮度/语言下要有不同模板或阈值策略。
- 每个模板保存原始截图、裁剪图、阈值、命中日志。

7. 能 OCR

验收：

- 首次模型下载成功。
- 缓存目录可写。
- 中文、英文、数字都能识别。
- 识别区域裁剪有效，不能每次全屏 OCR。

8. 能跑脚本

验收：

- `python -m imouse.script_runner <scenario.json> --dry-run` 通过。
- 单设备脚本包含截图、找图、点击、等待、人工 `record`。
- 真实运行后 evidence 中既有 API 结果，也有人工观察结果。
- 失败时能定位到具体步骤、设备 ID、错误文本和截图/模板路径。

## 群控验收流程

### 4 台小规模

目标：验证架构是否可并发。

- GUI 顶部 `Evidence` 设置为 `pilot_4_YYYYMMDD`，保持 `Record` 勾选。
- 准备 JSON 场景 `pilot_4_YYYYMMDD.json`，先 `--dry-run`。
- 4 台同时投屏。
- 4 台同时截图。
- 4 台依次点击。
- 4 台同步点击。
- 在 GUI 中保存分组 `pilot_4`，加载分组后再执行批量命令。
- GUI 设备表多选 4 台，分别执行批量 `Click`、`Swipe`、`Type`，保存每台设备的返回结果。
- 每轮批量命令后，用底部 `Manual` 行记录人工观察：每台设备是否真实点击、滑动、输入成功。
- 用 `python -m imouse.script_runner pilot_4_YYYYMMDD.json --run-id pilot_4_YYYYMMDD` 跑一轮脚本回归。
- 单台断开不影响其他设备。
- 连续 30 分钟内每 5 分钟保存一次状态：在线数、截图成功率、HID 成功率、投屏断线次数。
- 结束时点击 `Summary`，保存 `evidence/pilot_4_YYYYMMDD.md`。

### 10 台中规模

目标：验证现场可用性。

- GUI 顶部 `Evidence` 设置为 `stable_10_YYYYMMDD`，保持 `Record` 勾选。
- 准备 JSON 场景 `stable_10_YYYYMMDD.json`，包含分组批量操作和人工 `record` 步骤。
- 在 GUI 中保存分组 `stable_10`，重启 GUI 和内核服务后确认分组仍可加载。
- 连续运行 2 小时。
- 记录 CPU、内存、网络、FPS。
- 统计投屏断线次数。
- 统计 HID 失败次数。
- 统计脚本失败截图。
- 每 30 分钟做一次分组批量 `Click`、`Swipe`、`Type`，记录失败设备 ID 和错误文本。
- 每 30 分钟把人工观察结果写入 evidence，不能只保留 API 返回。
- 每 30 分钟跑一轮 JSON 场景，确保脚本化路径和 GUI 路径得到同样结果。
- 结束时点击 `Summary`，保存 JSONL 和 Markdown 汇总，作为研发复盘输入。

### 20 台以上压力

目标：验证是否接近 XP 类产品体验。

- 分组控制。
- 至少拆成 `batch_a`、`batch_b` 两个分组，分别运行和同时运行各测一轮。
- 批量重连。
- 批量启动/暂停/停止脚本。
- UI 不假死。
- 日志可按设备过滤。
- 失败设备隔离，不拖垮全局。
- 如果任一分组失败率明显高于其他分组，先排查 Hub、供电、网络和线材，再排查软件调度。

## 阶段门验收命令

每轮现场测试结束后，先生成 evidence 汇总，再运行对应阶段门。验收器只检查证据硬门槛，不能替代人眼确认 iPhone 已真实响应。

```powershell
.\.venv\Scripts\python -m imouse.evidence_report evidence\single_dev1_YYYYMMDD.jsonl
.\.venv\Scripts\python -m imouse.acceptance evidence\single_dev1_YYYYMMDD.jsonl --gate p1 --markdown evidence\single_dev1_YYYYMMDD_acceptance.md
```

晋级规则：

- P1 单设备必须 `--gate p1` PASS 后才能进入 P2。
- P2 单设备 30 分钟稳定性建议连续两轮 PASS 后再进入 P3。
- P3 4 台试点必须 `--gate p3` PASS，并且人工观察确认单台失败可隔离。
- P4 10 台 2 小时稳定性必须 `--gate p4` PASS，并且失败设备、Hub、线材、投屏组件都能追溯。

## 常见问题与处理

### AirPlay 找不到接收端

排查：

- 是否同一网段。
- AP 是否开启客户端隔离。
- Windows 防火墙是否拦截。
- 接收端服务名是否重复。
- Bonjour/mDNS 是否被网络设备过滤。

### 投屏黑屏或花屏

排查：

- 编解码格式是否不兼容。
- H264/H265 硬解是否可用。
- 显卡驱动是否异常。
- 是否同时开启太多投屏窗口。
- 是否被锁屏或系统弹窗遮挡。

### 点击偏移

排查：

- 截图尺寸是否等于真实坐标空间。
- 投屏窗口是否被缩放。
- 是否有标题栏、黑边、裁剪。
- 横竖屏方向是否已更新。
- Retina 缩放比例是否被重复换算。

### 找图误判

排查：

- 模板是否纯色或低纹理。
- 阈值是否过低。
- 是否未限定搜索区域。
- 是否不同主题/语言共用模板。
- 是否有透明图但未做 alpha 处理。

### OCR 无法启动

排查：

- PaddleOCR 是否能导入。
- 模型缓存目录是否可写。
- 首次运行是否能下载模型。
- 版本是否从 2.x 升到 3.x 导致返回结构变化。

### HID 无响应

排查：

- 串口是否被其他进程占用。
- 波特率是否正确。
- 固件版本是否匹配。
- USB Hub 是否供电不足。
- iPhone 是否识别到鼠标/键盘。
- 是否有按键或鼠标按钮未释放。

### Windows 控制台乱码或崩溃

处理：

- 命令行输出尽量避免 emoji 和特殊符号。
- 文档使用 UTF-8。
- 日志文件统一 UTF-8。
- PowerShell 中必要时设置 `PYTHONUTF8=1`。

## 现场记录模板

每次测试至少记录：

- 日期。
- 代码版本。
- PC 型号和系统。
- Python 版本。
- 投屏组件版本。
- 设备数量。
- iOS 版本列表。
- 硬件固件版本。
- 网络拓扑。
- 运行时长。
- 分组名和组内设备 ID。
- Evidence run id。
- JSONL 证据路径。
- Markdown 汇总路径。
- 失败设备编号。
- 失败截图。
- 日志路径。
- 复现步骤。

失败分类建议统一写入备注或 `details`：

- `airplay_discovery`：找不到投屏接收端。
- `airplay_stream`：黑屏、花屏、断线、延迟异常。
- `capture`：截图失败或尺寸异常。
- `vision_template`：找图误判或漏判。
- `vision_color`：找色误判或漏判。
- `ocr`：模型、缓存、识别结果异常。
- `hid`：鼠标/键盘无响应、按下未释放、坐标偏移。
- `group_dispatch`：分组缺设备、重复设备、单台失败影响全局。
- `business_state`：业务页面变化导致脚本目标不存在。
